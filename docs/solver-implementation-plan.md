# 4번 출력 확보 후 5–7번 구현 계획

검토일: 2026-11-15.

## 작업 원칙

- 사용자가 제시한 1–7번 흐름을 따른다.
- `minjun/constraint-solver` 브랜치의 코드·계약·UI·제한을 사용하거나 재사용하지 않는다.
- 4번의 실제 R → M JSON을 확보하기 전에는 solver 입력 계약을 확정하거나 구현을 시작하지 않는다.
- 이전 문서의 M 브랜치 재사용 제안과 제안 JSON은 철회한다. 이 문서는 그 계획을 대체한다.

## 현재 직접 확인한 범위

1. 원격 브랜치를 조회했다. `main`은 `cbaaf8e`, `riley/llm-setup`은 `36a2817`이며 추가 R 브랜치는 보이지 않았다.
2. R의 [PR #2](https://github.com/ucla-cs188-fall26/travel-planner/pull/2)를 확인했다. 본문은 “Add qwen 3.8 flash integration”이며 댓글이나 실제 출력 JSON은 없다.
3. `backend/llm.py`에는 일반 LLM 호출 및 Pydantic JSON 파싱 헬퍼가 있다. 이 헬퍼를 호출해 여행 제약을 추출하는 코드나 작업별 프롬프트는 공유 코드에서 찾지 못했다.
4. `backend/schemas.py`에는 ChatRequest/ChatResponse/Trip/Stop이 있다. ChatResponse.extracted는 자유 형식 딕셔너리다. 4번의 최종 JSON을 규정하는 전용 모델과 실제 응답 샘플은 확인되지 않았다.
5. `/api/chat` 라우트는 `mock-server/server.js`에서 fixture를 반환한다. `shared/fixtures/chat-response.json`은 실제 LLM 응답을 캡처한 증거가 아니다.
6. 로컬 프런트엔드는 `useMock: true`, `apiBaseUrl: '/api'`이고, `/api` 프록시는 localhost:3000을 가리킨다. 검사 시 4200 프런트엔드만 리스닝했고 3000/8000에는 서비스가 없었다.
7. 이 작업 폴더에는 `.env`, `backend/.env`, backend Python 가상환경이 없다. 현재 셸에도 API_KEY/BASE_URL/MODEL이 설정되어 있지 않다. 비밀 값은 조회하거나 출력하지 않았다.

따라서 현재 접근 가능한 저장소·PR·로컬 실행 상태만으로는 **R이 실제 생성한 4번의 결과를 확보하거나 재현할 수 없다.** 이는 R이 별도 환경에서 완료한 작업의 존재 여부를 판단한 것이 아니다.

## 실제 결과를 확보하는 방법

### A. R이 코드를 따로 갖고 있는 경우

가장 좋은 방법은 실제 추출 함수, 사용하는 스키마·프롬프트, 실행 예제 입력, 출력 JSON을 함께 확보하는 것이다. 별도 브랜치가 있다면 해당 브랜치를 읽기 전용으로 검사한다.

R에게 전달할 요청 예시:

> 5번 Z3 solver 연결을 위해 4번에서 실제 반환하는 JSON 한 개와 그때 사용한 입력을 공유해 줄 수 있어? anchors, preferences, special notes가 포함된 예시가 필요해. 가능하면 추출 함수·스키마가 있는 브랜치/파일이나 실행 방법도 알려줘. 예산 단위와 hard/soft 구분이 이미 정해져 있다면 그것도 같이 부탁해.

API 키는 공유할 필요가 없다. 개인정보는 익명화해도 된다.

### B. 실제 앱이나 API가 실행 중인 경우

실제 API 주소나 실행 중인 앱 주소를 알면 직접 호출하거나 브라우저에서 결과를 확인할 수 있다. 다른 사람에게 메시지를 보내지는 않는다.

사용자가 브라우저에서 확인하는 순서:

1. 실제 백엔드에 연결된 여행 앱을 연다.
2. 개발자 도구 → Network → Fetch/XHR를 연다.
3. anchor, 선호, 특별 메모를 입력해 정보 수집을 완료한다.
4. 제약 생성 요청을 찾는다. 현재 프런트엔드의 채팅 경로는 `/api/chat`이지만 실제 구현 경로는 다를 수 있다.
5. Request Payload와 Response JSON을 복사한다. 쿠키·Authorization 헤더가 들어가는 전체 HAR/cURL 대신 JSON 본문만 전달한다.
6. 응답이 mock fixture인지 확인한다. 현재 로컬 설정으로는 실제 R 출력의 증거가 되지 않는다.

4번의 결과가 백엔드 내부에서만 만들어진다면 Network 응답에 없을 수 있다. 이 경우 R의 추출 함수에서 M으로 전달하기 직전의 객체를 JSON 파일로 저장해야 한다. Pydantic 객체라면 그 지점에서 `result.model_dump_json(indent=2)`로 내용을 확인할 수 있다. 실제 함수명과 저장 위치는 구현을 확인한 후 정한다.

### C. API 호출로 재현하는 경우

실제 endpoint, 요청 스키마, 인증 방법 또는 R의 실행 스크립트를 먼저 확보한다. 그 뒤 동일 입력으로 요청하고 실제 응답을 캡처한다. 일반 `ask_json()`에 새 프롬프트를 임의로 넣어 얻은 응답은 기존 4번의 출력으로 취급하지 않는다.

## 확보할 최소 자료

- 익명화된 입력 1개: 여행 날짜·목적지·구성원 선호·anchor·특별 메모.
- 그 입력으로 실제 실행한 4번의 출력 JSON 1개.
- 생성 위치: API 경로 또는 Python 함수/파일, 가능하면 commit/브랜치.
- 기존에 정해진 단위나 의미: 예산 통화와 인당/그룹·일별/전체 범위, 시간대, 필수/선호 구분.

추가로 날짜가 정해진 anchor와 단순 방문 필수 장소가 어떻게 구분되는지, 누락/충돌 상태가 어떻게 표현되는지 확인한다. 정해져 있지 않은 항목은 실제 JSON 검토 후 R과 합의할 항목으로 기록한다.

실제 출력은 출처와 함께 `shared/fixtures/constraints-from-r.json` 같은 fixture로 보관할 수 있다. 아직 이 파일을 만들지 않았으며 예시 값을 실제 출력처럼 채워 넣지 않는다.

## 확보 후 수행할 작업

1. 실제 JSON의 필드를 표로 정리한다. 필드별 타입·단위·필수 여부·Z3 매핑·누락 데이터를 구분한다.
2. R의 기존 출력을 최대한 유지하며 M의 입력 검증·정규화 계층을 설계한다. 표현할 수 없는 특별 메모나 필수 데이터는 명시적으로 처리한다.
3. 5번 구현: 활동 후보·운영 시간·소요 시간·이동 데이터가 어디서 오는지 확정한 뒤 Z3로 일정을 생성한다.
4. 6번 구현: 실제 출력 일정을 고정한 검증과 알고리즘 기반 재배치를 구현한다. 필수 조건 충돌은 임의 완화하지 않고 R에 원인을 전달한다. 반복의 종료 조건을 둔다.
5. 7번 구현: 검증된 일정 JSON을 현재 프런트엔드 Stop 스키마에 맞춰 planner에 표시한다.

이번 변경은 계획 문서 수정뿐이다. solver 또는 R의 로직을 변경하거나 LLM을 호출하지 않았다.
